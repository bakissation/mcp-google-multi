# Implementation notes

Contributor-facing rationale for non-obvious implementation choices — why the code is the way it is, not how to use it. Back to the [README](../README.md).

## Token store

### Windows rename retry (`renameWithRetry`, `src/token-store.ts`)

`renameWithRetry` exists because Windows uses classic rename semantics (`MoveFileExW` without POSIX semantics): replacing a token file that another process momentarily holds open — a concurrent `readToken`, an antivirus scanner, or a search indexer — fails with a transient `EPERM`, `EACCES`, or `EBUSY`. Reads deliberately take no lock, so the token write lock cannot prevent this collision; a short bounded retry (`RENAME_ATTEMPTS` with linear backoff) absorbs it instead. POSIX rename never fails this way, so the retry loop is effectively inert on Linux and macOS.

### Lock liveness (`withFileLock`, `src/fs-atomic.ts`)

A write through `withFileLock` (`config.json`, the token and refresh stores, master-key provisioning, usage metrics) takes a hardlink lock: the writer creates an owner file holding its pid, then links it to the lock name. The owner file stays linked while the lock is held, and its name records the holder's process instance: pid, PID namespace id (`/proc/self/ns/pid`), start time in clock ticks since boot (`/proc/self/stat`) and a boot id prefix. A part the writer cannot read is recorded as `host` or `0`; the start time is also `0` when `/proc` belongs to another PID namespace, since no pid can be looked up in it. The lock body stays the bare pid, so an older reader parses it as before. A pid alone cannot name a process across a container restart: the new container's server usually has the old one's pid, and the kernel often hands the new PID namespace the old one's id as well. Only the start time differs. A waiter decides whether a holder is dead as follows:

- **Same namespace id and boot, all parts known:** no two live namespaces share an id, so the recorded pid is one the waiter can look up. The holder is alive only if the process at that pid now has the recorded start time. A lock from the previous container, or from an earlier process that had the same pid, is therefore broken at once.
- **Another namespace or another boot** (a sibling container, say): the pid means nothing here, so the lock is dead once it is 60 s old (`LOCK_LEASE_MS`). Every hold is a short synchronous section, so only a frozen process (`docker pause`, SIGSTOP) holds that long.
- **Same namespace, identity not fully known** (macOS, Windows, a `/proc` from another namespace, or an unreadable boot id): the signal-0 probe (ESRCH is dead) plus the lease; a lock naming the waiter's own pid is dead if it was written before the waiter started.
- **No owner file** (an older writer): the probe plus the lease.

One waiter at a time breaks a dead lock, under a `.break` file created with `O_EXCL`, so two waiters cannot both break it and delete each other's new lock. Under it, the waiter reads the holder again and breaks only if the lock still has the same inode, body, mtime and owner file: a new lock can get the dead one's freed inode, but not its owner file's random name. A breaker removes the `.break` file only if it still holds its own random token, and a waiter clears one that is a symlink or other non-regular file (a directory there is an error), or is dated 2 s or more from the current time in either direction. A holder releases the lock only while its own owner file is still linked to it, so a holder whose lock was broken never removes its successor's. On a filesystem that reports a different inode number for each name of a file (some CIFS, sshfs and FUSE mounts), the owner file cannot vouch for the lock; the holder then releases unconditionally and waiters fall back to the probe and the lease. The lease compares the waiter's clock with the lock's mtime, which assumes the writers share a clock (containers on one host do).

### Refresh rotation checks the subject first (`RefreshStore.rotate`, `src/mcp-token.ts`)

`rotate` spends the presented token (advances its family's generation) in the same critical section that mints its successor. A caller that asked "is this subject still served?" only after `rotate` returned could not fail safe: on a transient error the old token is already spent and the client is signed out. The optional `accept(sub)` therefore runs inside the lock, after the record is found and before any mutation. A `false` drops every session of that sub (the `purgeTenant` loop), so a later `true` does not revive the family; a throw leaves the file untouched. The reuse branches never call it, so theft detection is unchanged.

`/token` wires `AuthServerDeps.subjectActive` into `accept` and converts a throw from it into a module-private error class inside the callback, so the route answers 503 `temporarily_unavailable` only for that failure; any other throw from the store still propagates. The route never puts the thrown message in the body; it goes to the server log, as the transport's catch-all 500 does with any other throw. The authorization-code grant checks the subject after its last `await` and immediately before `issue`, so within one process nothing can interleave between the check and the write.

### Refresh families count generations (`RefreshStore`, `src/mcp-token.ts`)

Reuse of a rotated-away refresh token revokes its family (OAuth 2.1 section 4.14). The evidence used to be a list of every rotated-away token. A list has to be capped, and whoever held a family's live token could rotate it past the cap, after which the real client's stolen-away token was only refused while the thief kept the session. Evidence that never expires has to stop growing with rotations, so each token now carries its family id and a generation number: `r1.` + base64url(family id 16 bytes, generation uint32 big-endian, 16 random bytes, HMAC-SHA256 of those under a key derived from `MASTER_KEY` with HKDF, info `mcp-google-multi:refresh-mac:v1`). A `MASTER_KEY` that is not base64 of 32 bytes is a passphrase, and goes through scrypt (N 2^15, r 8, p 1, salt `mcp-google-multi:refresh-mac:scrypt:v1`) before HKDF, once per process: every client holds MAC'd tokens, and without a work factor one leaked token would test passphrase guesses at hash speed. For each family the store keeps the subject, the current generation, a SHA-256 of the current token's bytes, the sign-in time and the last-use time.

The length, canonical base64url and MAC checks run before the file lock, with constant-time compares, so a forged token costs one HMAC and never touches the file. A token for an unknown family is refused (the family was revoked, expired, dropped or purged). An older generation for a live family revokes it: it is a rotated-away token, and the MAC proves the server minted it, so nobody without the key can revoke someone else's session by forging one. A newer generation means the store lost a write the client saw (a power loss before the rename reached disk, a backup restore, a lock broken after its lease), and the same generation with another random part means two writers rotated the same generation. Both drop the family too (the client signs in again) but log `ahead` or `mismatch`, not `reuse`, because neither is evidence of theft. The current token rotates: generation plus one, a new random part, the last-use time moved forward, the sign-in time and subject copied forward. A family at the last generation (2^32 - 1) is dropped instead of rotated. The stored hash means the decrypted store holds no usable new-format token. The MAC covers the random part, so an altered current token fails the MAC instead of reaching a drop branch. Revoke and drop lines carry a short tag derived from the family id (`refreshFamilyTagger` computes the same tag from a token, without the store); expiry, `accept` and clock lines carry only a count. No line carries the token or the subject, and lines are written only after the file is.

Files from releases before the format change still load. Every record is validated on load and a malformed one is dropped. Legacy records stay under `active` and `spent` with their old meaning. A legacy token that is still active is exchanged on its next rotation for a new family (generation 0, sign-in time = the legacy record's last-issue time, since the real one was never stored), and the legacy family id is recorded on it. The legacy token joins `spent`, and every legacy `spent` entry of that family keeps revoking the new family. New code adds to `spent` only one entry per migration: each save drops the entries of legacy families with no live record in either format, and the old per-subject cap is gone because it could no longer trigger. Once a process has read a file with no legacy records (a read that fails does not count), it refuses legacy-shaped tokens before the lock as well. An older release reading a new file ignores `format` and `families`, refuses every new token as unknown, and drops the new families the first time it writes. Clients sign in again; nothing is accepted that should not be. A file whose `format` is newer than this release knows is refused rather than read as empty, because an empty read is followed by a write that would erase it.

Lifetimes are optional (`maxAgeSec` from sign-in, `idleSec` from the last issue or rotation; unset means unlimited). Every locked issue and rotation first drops expired sessions of every subject, in both formats, so with a lifetime set the store holds only sessions used within it. Expiry is checked before reuse and before `accept`, so a dead session is refused without asking whether its subject is still served. The last-use time takes the larger of the stored time and the caller's, because `now()` is read before the lock wait and a later writer can hold an earlier time. Timestamps more than five minutes ahead of the clock are pulled back to it on load, so a session written while the clock ran ahead cannot outlive its limit by the size of the jump. A clock that jumps forward makes every session look expired, and the prune deletes them: that fails closed (everyone signs in again), and a prune that drops every session logs that the clock may be wrong. A legacy record has only its last issue or rotation time, which serves as both its sign-in and its last-use time. `purgeTenant` takes no clock, so it neither clamps nor prunes.

A revoke, drop or expiry does not recall access tokens already minted from the family; they live out their `accessTtlSec` (600 s by default).

## Admin SDK

### Why admin tools are per-account opt-in (`ADMIN_SCOPES`, `src/auth.ts`)

The Admin SDK requires a Workspace account with admin privileges; consumer @gmail.com accounts always get a 403. Strictly speaking, the only person with admin rights over a @gmail.com account is a Corporate Operations Engineer on Google's internal Techstop helpdesk — and if that's you, an MCP server is really not how you should be doing this. Requesting admin scopes on an account that cannot use them would only add consent-screen noise, so `GOOGLE_ADMIN_ACCOUNTS` grants them per-account instead of globally.

## Networking

### Why the server raises Node's happy-eyeballs timeout (`applyNetTuning`, `src/net-tuning.ts`)

Node enables Happy Eyeballs (`autoSelectFamily`) by default since v20 and gives each address-family connect attempt 250ms (`autoSelectFamilyAttemptTimeout`). On a high-latency link to a distant Google edge, or when the ISP router advertises a dead IPv6 route, that budget aborts the IPv6 attempt *and* the IPv4 attempt, so every Google call fails with `ETIMEDOUT` while `curl` (which waits normally) works. Node itself raised the default to 500ms ([nodejs/node#60334](https://github.com/nodejs/node/pull/60334)) but only from v25.2; every LTS line this package supports ships 250ms, and the real fix (RFC 8305 parallel attempts, [nodejs/node#48145](https://github.com/nodejs/node/issues/48145)) is still open. The server therefore raises the process-wide default to 2000ms at startup. The trade-off is a slower failover when one address family hangs rather than fails fast — acceptable for a personal MCP server, not worth per-request agent plumbing through gaxios and undici. The tuning is skipped whenever the user passes `--network-family-autoselection-attempt-timeout` or `--no-network-family-autoselection` (via CLI or `NODE_OPTIONS`), and it never lowers a value that is already at or above 2000ms.

### How the section-6 API-enablement probe picks its reads (`API_PROBES`, `src/api-probe.ts`)

Probes are selected by the **granted scopes** on the probed account, not by the registered services: probing an ungranted service can only produce `insufficient_scope`, which says nothing about enablement. Services with no no-argument read (Sheets, Docs, Forms) are probed with a GET on a nonexistent id — Google checks `accessNotConfigured`/`SERVICE_DISABLED` before routing, so a 404 still proves the API is enabled. Admin SDK is deliberately unprobed (role-dependent: a 403 on a non-admin account is ambiguous). A connect-level failure aborts the run so section 6 reports one WARN with the syscall code instead of a column of unknowns. The probe uses `getClient`, so an expired-refreshable token may refresh and re-encrypt on disk — the same cache write every tool call performs; BR7's "no mutation" bars config/token *destruction*, not the refresh path.

### Why connect failures get their own `network_error` envelope (`netCodeOf`, `src/tools/_errors.ts`)

The Google API path is gaxios → node-fetch → `node:https`. When the happy-eyeballs `AggregateError` (whose `message` is empty) reaches node-fetch, its `FetchError` keeps only the `code`/`syscall` and discards the error object, producing the famously unhelpful `request to <url> failed, reason: ` with the real signal hiding in `error.code`. `mapGoogleError` previously fed `error.code` through `Number()` (built for HTTP statuses), so `ETIMEDOUT` was dropped and the envelope said `upstream_error, retriable: false` — wrong on both counts. `netCodeOf` walks the cause chain (GaxiosError → FetchError; undici `TypeError` → `AggregateError.errors`) for known connect/DNS syscall codes and returns a `network_error` envelope that names the code, marks transient codes retriable, and points at the happy-eyeballs flag. Per-address sub-errors are only available on undici call sites; node-fetch destroys them upstream.

## Executor

### Request bodies on GET/HEAD (`resolveRequestBody`, `src/executor.ts`)

`executeApiMethod` strips request bodies from GET/HEAD requests before dispatch:

- gaxios stringifies any object passed as `data` without checking the HTTP verb, and undici (Node's `fetch`) rejects GET/HEAD requests that carry a body (`Request with GET/HEAD method cannot have body`). A caller-supplied `{}` body on a read tool would therefore crash the request.
- Stripping is lossless: no Google Discovery GET/HEAD method declares a request schema, so there is never a legitimate GET/HEAD body to preserve.
- Write verbs keep the usual semantics: `null`/`undefined` means no body is sent.

## Argument normalization

`src/arg-normalize.ts` renames snake_case `tools/call` argument keys to their declared camelCase twins (e.g. `thread_id` → `threadId`) before SDK validation, at the transport `onmessage` seam. The seam is deliberate: the SDK advertises an EMPTY input schema in `tools/list` for any non-object schema wrapper (pipe/preprocess), so schema-level normalization would blank every tool's advertised parameters, while the JSON-RPC message shape is versioned MCP spec. The rename is lossless by construction (sent key unknown to the schema, camel twin declared, twin not also sent) and each one logs key names — never values — to stderr. Because clients string-encode values for keys absent from the advertised schema, a renamed key's value is also coerced to the declared scalar kind when it parses cleanly (`"2"` → `2` for a number field, `"true"` → `true` for a boolean); declared keys' values are never touched. `GOOGLE_ARG_NORMALIZE=off` disables it.

The same seam has a second job: **unknown-argument screening** (`src/arg-strict.ts`, `GOOGLE_ARG_UNKNOWN`). zod strips undeclared keys before a handler runs, so a misremembered parameter name used to produce a *successful* call with wrong behavior: `parentId` passed to `drive_create_folder` (which declares `parentFolderId`) was dropped and the folder was created in My Drive root. Because the seam already holds the tool's declared key set, it can see exactly what the schema is about to discard. It never rewrites a key and never touches a value: rewriting on a guess would send a real value to Google, which is worse than refusing. Renaming runs first, so a snake_case twin of a declared key is a fix rather than an unknown argument. Suggestions are tiered (case/separator-insensitive equality, then token subset, then containment, then edit distance) because plain edit distance cannot reach the motivating case: `parentid` to `parentfolderid` is distance 6. When nothing matches, the hint names how sibling tools in the same service spell the concept. The default is `reject`: `warn` shipped first as pure observability, but it reaches stderr only, so the client still sees a confident success for a call the server did not perform. Never screened: keys starting with `_` (MCP and vendor metadata), keys containing `/` (namespaced extensions), the four client-artifact names (`random_string`, the probe some clients send to a tool they read as argument-less, plus `toolCallId`/`tool_call_id`/`tool_call_description`, which bridges have been seen folding into `arguments` instead of `params._meta` where the spec puts them), tools declaring no arguments, and a key whose declared twin the same call also sent (that call already behaves correctly, so it is left alone). A sibling-spelling hint only ever names a tool that is currently advertised in `tools/list`, since naming a hidden one turns a recoverable error into a dead end. Dotted keys are deliberately *not* exempt, since 41 declared parameters genuinely contain a dot. The escape hatch needs no exemption either: its open-endedness lives in the *values* of `queryParams`/`body`, never in its fixed top-level keys.

The seam also owns one **outbound** job (`withValidationEnvelope`). The SDK validates tool input itself, throws, and catches its own throw in the same `tools/call` handler, returning `{content:[{type:'text',text:<prose>}],isError:true}`. No handler of ours runs, so no envelope exists and the client used to get free text with no slug, no hint and no `retriable`, which is precisely the contract break the hint floor exists to prevent. The wrapper converts that frame, and only that frame: a handler's own answer, whether JSON or the account wizard's prose, passes through untouched, because only the SDK's two prefixes (`Input validation error:`, `Output validation error:`) are rewritten. It is wrapped **innermost**, below the metrics tap, because outbound runs outermost-first: the tap must still see the original prose to classify it as `schema_validation`, while the client sees the envelope. The account is recovered from the pending request, since the registry injects the default only after validation has already failed.

## HTTP transport

### Lane bound (`maxQueuedPerLane`, `src/http-transport.ts`)

Every `/mcp` request runs its connect and dispatch on its resolved server's lane, one at a time, because a `McpServer` holds one connected transport. The lane is a promise chain with no count, so without a bound a caller admitted faster than its lane drains grows the queue for as long as it keeps sending, each entry holding its buffered body. `maxQueuedPerLane` counts a request against its server from the moment `resolveServer` returns until its lane run settles, which covers reading the body, waiting in the queue and running. The check sits before the body read so a refused request never buffers its body, and the count is per server so one caller's full lane never refuses another's. The slot is released in a `finally` around everything after admission: a body error, a batch refusal, a dispatch deadline and a client that left all release it. A request whose client left while it was being authenticated or resolved has already been destroyed, and Node emits neither `end` nor `error` again once listeners attach, so the body read refuses a destroyed request at once rather than waiting forever and holding its slot. The count bounds queue depth, not queue time: each dispatch keeps its own deadline, so a queued request can wait up to `maxQueuedPerLane - 1` deadlines behind hung calls.

### Client-gone skip (`src/http-transport.ts`)

The dispatch deadline and the disconnect listener are both created when a request's lane run starts, so a request waiting in the queue has neither, and `server.requestTimeout` stops applying once the body is fully received. A queued `gmail_send` whose client gave up would therefore still send when its turn came, and the client's retry could send it again. The host registers a `close` listener on the response as soon as the request passes the front guard; at lane entry a set flag, or a destroyed socket, skips connect and dispatch and logs `499 client_gone path=/mcp`. The socket check is needed because Node emits that `close` only on the response currently writing to the socket: a response pipelined behind another on the same connection stays queued, and when the client drops the connection it never emits `close` at all. It only skips work whose response can no longer be delivered, so it is on regardless of options.

### Graceful close (`HttpTransportHost.close({ graceMs })`, `src/http-transport.ts`)

`close()` with no argument cuts every connection at once, as it always has. With `graceMs` one rule governs the close: every request accepted before `close()` began runs to completion and gets its answer delivered within `graceMs`, and a request that arrives after it began is never handled, not even authenticated. The host stops listening, waits for every socket to close and every `handle()` to settle, and only then resolves; after `graceMs` it cuts what is left. Node's `server.close()` cannot be used as is: since Node 19 it calls `closeIdleConnections()`, which skips a socket only while its response has not ended, so a response that has ended but is still flushing (any body larger than the socket buffers, which a `drive_read` or an export easily is) counts as idle and is destroyed mid-body. The host therefore suppresses that call for the duration of `close()` and closes idle sockets itself from its own bookkeeping: every open socket, per socket the number of accepted requests whose response has not settled (raised in the request listener before `handle()`, lowered when that response finishes or closes) together with the last of them, which sockets have accepted any request, and every unsettled `handle()`. At close start a socket that never accepted a request is destroyed, which covers a connection whose first request headers are still arriving. A socket that has accepted requests but has nothing pending is ended at once, a lingering close like any other (next paragraph), not destroyed: nothing pending only means its last response finished writing, and a large one can still sit in the kernel's buffers while a slow client reads it, so a destroy would reset the connection under that tail as soon as the client sends anything more, a request pipelined behind it say. An idle keep-alive client closes its side on that end at once. On every other socket only the last pending response is marked: it gets `Connection: close` if its headers are not yet sent, and the socket is ended when its count reaches zero, which is when that last response finishes, since responses on a connection finish in order. No response ahead of it ever ends the socket, so a call pipelined behind a streaming route response, or a route behind an `/mcp` call that has not answered yet, is still delivered, and a request already waiting on its lane when the close began runs at its turn. A request pipelined after the close began is ignored by the request listener and its connection ends after the last response it owes, which RFC 9112 section 9.6 allows; nothing of it ran, so the client can retry it safely. The client-gone skip still applies at the lane turn: a pre-close request whose socket died is not dispatched. A socket's entry is deleted when its count reaches zero and when the socket closes, because Node never emits `close` on a response still queued behind another, so the default path holds one entry per socket with a request in flight and one per unsettled `handle()`, and a client that drops a connection with requests still queued on it leaves nothing behind. Waiting on `handle()` as well as on sockets covers a request whose client left while it was being authenticated or resolved: its socket is gone but its work is not.

Ending a socket is a lingering close. Destroying it once its last response is flushed, as Node does after a `Connection: close` response, resets the connection whenever the client is still sending, say a large body pipelined after the close began: the kernel answers unread or later input with a reset and drops whatever of the response is still in its send buffer, so a slow reader loses the tail. The host therefore only calls `socket.end()` and waits for the client's FIN to close the socket, or for `graceMs` to end and the rest to be cut; it also disarms the keep-alive timer Node arms when a response finishes, which would otherwise destroy the socket about 6 s later with the same reset. At close start every socket that has accepted a request gets a `destroySoon` that does the same lingering end, since that is the hook Node calls after a `Connection: close` response. A socket with nothing pending is ended the same way (its last response may still be in the kernel's buffers), so a request racing onto an idle served connection after the close began is held by the rule below and keeps the close waiting until `graceMs`. A request that arrives while closing is never answered, so Node never frees it: its response waits in the connection's outgoing queue behind the ones owed, and Node's own pipelining backpressure, which pauses a socket only while written output is backed up, never engages. A client pipelining tiny requests behind a held response could thus grow the heap without limit until the grace ends. So the first such request stops the socket from reading for good: `socket.pause()`, with `resume` replaced by a no-op on that socket, because Node resumes a socket after every parsed request (`parserOnMessageComplete`) and when its output drains. TCP flow control then stops the client. The requests already in the read being parsed still arrive (at most one read, 64 KiB, of input), and their bodies are left unread. Writing needs no reading, so the responses owed are still delivered whole. The cost is that such a socket can no longer see the client's FIN, so it is closed when `graceMs` ends by `closeAllConnections()`; a client that sends nothing after the close still gets the prompt lingering close. A repeat `close({ graceMs })` returns the close under way, keeping the first grace: running the close start again would arm a second timer, and a shorter one would cut what the first still lets finish. `close()` with no argument during a graceful close cuts every connection at once as it always does; the graceful call still resolves once its handlers settle or its grace ends. `close()` waits on each `handle()` through a promise that never rejects: `fail()` cuts a response whose headers are already sent instead of writing a 500 over it, and if answering a failure throws anyway the response is destroyed, so neither `close()` nor the process sees a rejection, and the close tail runs in a `finally`. `graceMs` is validated before anything closes (a number from 0 to 2^31-1), because `setTimeout` fires at once for a larger delay, `Infinity` included, which would cut every connection at the start of the close.

## OAuth authorization server

### Owner sign-in browser binding (`toGoogle`, `/callback`, `src/oauth-as.ts`)

The owner sign-in (`flow=owner_gate`) hands the Google leg a signed state, and that state alone used to be enough to finish it. DCR is open to any client, so anyone could register a client with their own `redirect_uri`, approve its consent interstitial themselves, and forward the resulting Google URL; whoever signed in there had their subject's authorization code delivered to that `redirect_uri`. The redirect to Google therefore also sets a cookie holding 32 random bytes and signs their sha256 into the state (`StatePayload.bind`). `/callback` spends the state, then, for owner_gate only, reads the cookie the state names and compares its hash with `timingSafeEqual`. A missing or different cookie answers 400 `E_BROWSER_MISMATCH` as a plain page: no redirect to the client, no code, and neither `exchangeCode` nor `resolveSubject` runs, so nothing is looked up and no invite is spent. The log line says only `missing` or `mismatch`, never the cookie or the state. The check runs after the replay spend so a refused callback URL cannot be finished later from the browser that holds the cookie. That needs the spend to be recorded and kept: `ReplayGuard` never forgets a live jti (a full guard refuses, 503, instead of evicting its oldest entry, which a flood of cheap sign-in steps could otherwise push out), and the state's slot is reserved when it is minted, so a flood that fills the guard before the callback arrives is refused at `/authorize` and the callback still finds its slot. The guard is in memory and a restart empties it, so states, approvals and authorization codes are signed with a key each AuthServer generates (one per `buildAuthServer` call), not with `MCP_JWT_KEY`, and are checked against the AuthServer's own clock, the one the guard uses: after a restart every sign-in in flight fails verification and starts again, so neither a callback refused before the restart nor a state that was never reserved in the new process can be finished. On success the cookie is cleared.

Each flow gets its own cookie name (`mgm-og-` plus 16 characters of the hash), so two sign-ins started in one browser, say two clients connecting at once, do not overwrite each other. It is `HttpOnly; SameSite=Lax; Path=/; Max-Age=600` (the state TTL): Lax is still sent on the top-level navigation back from Google. On an `https` base the name carries the `__Host-` prefix and the cookie is `Secure`, so no subdomain or plain-http page can plant one. An `http` base drops both: the prefix requires `Secure`, and browsers do not agree on accepting a `Secure` cookie over plain http even on loopback (WebKit has refused it for `localhost`), so the single owner's `http://127.0.0.1` flow would otherwise break. Plain http offers no transport secrecy anyway, and loopback cookies are shared by every port on the host, which only a local process can use. `alias_add` and `alias_reauth` set and check no cookie: the first is bound by the link its minting caller hands out, the second by the signed re-auth link and the alias's own email. The DCR interstitial is sent with `frame-ancestors 'none'` and `X-Frame-Options: DENY`, so another site cannot frame it and steer the owner's click on Approve.

### Code-exchange failures stay in the log (`/callback`, `src/oauth-as.ts`)

A 400 page is a completed response, so the transport's catch-all 500 never sees a failed exchange and cannot sanitize it. `/callback` therefore answers a fixed `invalid_grant` page itself and logs the thrown message through `logSafe`: a line break becomes a literal `\u000a` and the text is cut at 300 characters, so a multi-line upstream error stays one log line and cannot pass for a second one. A host that wraps `exchangeCode` to map Google errors to slugs can keep doing so; the browser sees the fixed page either way.

### CIMD fetch and cache (`fetchCimdDocument`, `src/ssrf-guard.ts`; `CimdClientCache`, `src/cimd-cache.ts`)

`GET /authorize` is unauthenticated, and a `client_id` on an allowlisted issuer with a path never seen before makes the server fetch a document, so that fetch is bounded on its own and in aggregate. `fetchCimdDocument` follows no redirect, as the CIMD draft requires (section 5): the issuer allowlist is checked on the `client_id` URL only, so a followed hop through an open redirect on an allowlisted host would fetch any document, and that document could claim the original `client_id` and skip the consent interstitial. One deadline (8 s) covers every attempt: each attempt's timer is the smaller of its own cap and the time left, and it is armed before the DNS lookup. `dns.lookup` cannot be cancelled: the attempt stops waiting on it, but `getaddrinfo` keeps its libuv threadpool thread until it returns. `fetch` resolves the host again when it connects, and that lookup can hang too, so an attempt that timed out is never retried, wherever it stalled: one fetch leaves at most one hung lookup behind. The default resolver also starts no lookup of its own while 4 it started have not returned, abandoned ones included; that fetch fails at once as transient (`EAI_AGAIN`), with no retry, instead of queueing behind them. The count is process-wide, as the threadpool is, and covers only these lookups, not the one `fetch` makes when it connects. Only a fast transient failure is retried (a reset, a refused connection, a resolver that could not answer this time, but not a timeout and not a name that does not exist), once, and only when the backoff fits in the time left. A failed attempt aborts its own request first, so a refused status hands its connection back without the body being read. The body cap is the draft's recommended 5 KB (section 8.7).

`CimdClientCache` runs at most 4 fetches at once. That cap alone does not bound the threadpool, since a permit is freed when a fetch gives up, not when its lookup returns. The lookup count above bounds the guard's own lookups, and the no-retry rule leaves at most one connect-time lookup per fetch beside them, which is not counted. With the default pool of 4, lookups that hang can still hold every thread until `getaddrinfo` returns, and async file system calls wait meanwhile, but a flood of distinct paths cannot queue the guard's lookups behind them. A host that needs the file system to stay responsive through a resolver outage can start with a larger `UV_THREADPOOL_SIZE`. A request for a `client_id` already being fetched waits on that fetch and takes no permit. The promise the waiters share never rejects: the request that started the fetch settles it from a `finally`, because neither core nor a host installs an `unhandledRejection` handler and Node exits on one. Over the cap `/authorize` answers 503 `temporarily_unavailable` with `Retry-After: 5`, not `invalid_client`, which clients and people read as a permanent misconfiguration. The cap is full exactly while someone floods random paths, so a document that validated in the last 24 hours is served instead of refusing, and a real client keeps signing in. Only a validated document is stored, as the draft requires (section 5.2: no caching of errors or invalid documents). A refetch whose failure says the document went bad (a 4xx other than 408 and 429, a redirect, an oversized or malformed body, a document that does not validate, a name that does not exist, an SSRF block) drops the stored copy, so such a document is never served stale. A failure that says nothing about the document (a timeout, a reset, a resolver that could not answer, HTTP 408, 429 or 5xx) keeps it, and while it validated less than 24 hours ago the request that fetched and every request waiting on it get that copy instead of the error, so an overloaded issuer does not sign every client out. The error itself is never stored, and the copy keeps its age, so the next request asks the issuer again. There is no negative cache: the attack varies the path, so a key on the full `client_id` never hits, a key on the host would refuse the real issuer, and the draft forbids caching errors anyway. The store holds 256 entries and drops the oldest first. The `CIMD busy` line is rate-limited to one a minute in core because over-cap requests arrive at any rate and core is the one place that sees them all.
