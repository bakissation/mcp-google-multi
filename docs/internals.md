# Implementation notes

Contributor-facing rationale for non-obvious implementation choices — why the code is the way it is, not how to use it. Back to the [README](../README.md).

## Token store

### KDF is compat-frozen (`deriveKey`, `src/token-store.ts`)

A generated `MASTER_KEY` is `randomBytes(32)` base64 and takes the raw path; only a human-chosen passphrase hits the bare-SHA-256 branch. That branch predates this release (v5) and cannot change: every existing encrypted token was written under it, and altering the derivation would make them all undecryptable; effectively bricking every linked account. `encryptToken`/`decryptToken`'s HKDF + `ENC_VERSION=2` envelope is the sanctioned post-6.0 hardening route for anything new; it layers on top of `deriveKey` rather than replacing it.

### Windows rename retry (`renameWithRetry`, `src/fs-atomic.ts`)

`renameWithRetry` exists because Windows uses classic rename semantics (`MoveFileExW` without POSIX semantics): replacing a token (or other atomically written) file that another process momentarily holds open — a concurrent `readToken`, an antivirus scanner, or a search indexer — fails with a transient `EPERM`, `EACCES`, or `EBUSY`. Reads deliberately take no lock, so the token write lock cannot prevent this collision; a short bounded retry (`RENAME_ATTEMPTS` with linear backoff) absorbs it instead. POSIX rename never fails this way, so the retry loop is effectively inert on Linux and macOS.

### Lock liveness (`withFileLock`, `src/fs-atomic.ts`)

A write through `withFileLock` (`config.json`, the token and refresh stores, master-key provisioning, usage metrics) takes a hardlink lock: the writer creates an owner file holding its pid, then links it to the lock name. The owner file stays linked while the lock is held, and its name records the holder's process instance: pid, PID namespace id (`/proc/self/ns/pid`), start time in clock ticks since boot (`/proc/self/stat`) and a boot id prefix. A part the writer cannot read is recorded as `host` or `0`; the start time is also `0` when `/proc` belongs to another PID namespace, since no pid can be looked up in it. The lock body stays the bare pid, so an older reader parses it as before. A pid alone cannot name a process across a container restart: the new container's server usually has the old one's pid, and the kernel often hands the new PID namespace the old one's id as well. Only the start time differs. A waiter decides whether a holder is dead as follows:

- **Same namespace id and boot, all parts known:** no two live namespaces share an id, so the recorded pid is one the waiter can look up. The holder is alive only if the process at that pid now has the recorded start time. A lock from the previous container, or from an earlier process that had the same pid, is therefore broken at once.
- **Another namespace or another boot** (a sibling container, say): the pid means nothing here, so the lock is dead once it is 60 s old (`LOCK_LEASE_MS`). Every hold is a short synchronous section, so only a frozen process (`docker pause`, SIGSTOP) holds that long.
- **Same namespace, identity not fully known** (macOS, Windows, a `/proc` from another namespace, or an unreadable boot id): the signal-0 probe (ESRCH is dead) plus the lease; a lock naming the waiter's own pid is dead if it was written before the waiter started.
- **No owner file** (an older writer): the probe plus the lease.

One waiter at a time breaks a dead lock, under a `.break` file created with `O_EXCL`, so two waiters cannot both break it and delete each other's new lock. Under it, the waiter reads the holder again and breaks only if the lock still has the same inode, body, mtime and owner file: a new lock can get the dead one's freed inode, but not its owner file's random name. A breaker removes the `.break` file only if it still holds its own random token, and a waiter clears one that is a symlink or other non-regular file (a directory there is an error), or is dated 2 s or more from the current time in either direction. A holder releases the lock only if it is still the exact file (inode and mtime) this call created, and its own owner file is still there to vouch for it: a holder whose lock was broken (the breaker removes a known owner file together with the lock) never removes its successor's. On a filesystem that reports a different inode number for each name of a file (some CIFS, sshfs and FUSE mounts), the owner file is never identical to the lock by that measure either, so the holder falls back to its own recorded identity for the lock, which a renamed-away name cannot spoof. The lease compares the waiter's clock with the lock's mtime, which assumes the writers share a clock (containers on one host do).

Android denies `link()` in an app's private storage (Termux) with `EACCES`, and some filesystems lack hard links entirely and return `EPERM`; either turns every lock attempt into a dead end with no fallback. There the lock is instead created directly with `O_EXCL`, carrying the bare pid a linked owner file would have carried; since it cannot be hard-linked to the owner file, the owner file is bound to it instead by a recorded identity: once the lock is written, its dev, ino and mtime are read back and stored as the owner file's content, and `readHolder` accepts an owner file whose name matches the lock's pid and whose recorded identity matches the lock's current `lstat`, exactly as it already accepts one hard-linked to it. That binding is a second write after the lock's own, so a reader can catch the owner file still holding its original placeholder body; a lock in that state is read as held, not dead, for the same `LOCK_WRITE_GRACE_MS` window as an empty one, and only once it ages past that window without a binding is it recovered as this file's own crash. Creating the lock itself is also two syscalls, open then write, so a waiter can catch it empty in between; an empty lock within `LOCK_WRITE_GRACE_MS` of the current time (in either direction, a clock can step back) is therefore read as still being written, not dead, and one outside that window is a crash between the two and is recovered like any other dead holder. A write failure between them (`ENOSPC`, say) removes the empty lock only if it is still the file this call just created, then rethrows rather than retrying: a write failure is not `link()` being denied again, so it is never read as another reason to fall back. The binding write itself can fail the same way, after the lock already holds our live pid; that failure removes the lock too, checked against the same recorded dev/ino/mtime, so a crash there cannot leave every other writer waiting out the full lease for a holder that never finished taking the lock.

### Refresh rotation checks the subject first (`RefreshStore.rotate`, `src/mcp-token.ts`)

`rotate` spends the presented token (advances its family's generation) in the same critical section that mints its successor. A caller that asked "is this subject still served?" only after `rotate` returned could not fail safe: on a transient error the old token is already spent and the client is signed out. The optional `accept(sub)` therefore runs inside the lock, after the record is found and before any mutation. A `false` drops every session of that sub (the `purgeTenant` loop), so a later `true` does not revive the family; a throw leaves the file untouched. The reuse branches never call it, so theft detection is unchanged.

`/token` wires `AuthServerDeps.subjectActive` into `accept` and converts a throw from it into a module-private error class inside the callback, so the route answers 503 `temporarily_unavailable` only for that failure; any other throw from the store still propagates. The route never puts the thrown message in the body; it goes to the server log, as the transport's catch-all 500 does with any other throw. The authorization-code grant checks the subject after its last `await` and immediately before `issue`, so within one process nothing can interleave between the check and the write.

### Refresh families count generations (`RefreshStore`, `src/mcp-token.ts`)

Reuse of a rotated-away refresh token revokes its family (OAuth 2.1 section 4.14). A list of every rotated-away token would have to be capped, and whoever held a family's live token could rotate it past the cap, after which the real client's stolen-away token would only be refused while the thief kept the session. Evidence that never expires has to stop growing with rotations, so each token carries its family id and a generation number: `r1.` + base64url(family id 16 bytes, generation uint32 big-endian, 16 random bytes, HMAC-SHA256 of those under a key derived from `MASTER_KEY` with HKDF, info `mcp-google-multi:refresh-mac:v1`). A `MASTER_KEY` that is not base64 of 32 bytes is a passphrase, and goes through scrypt (N 2^15, r 8, p 1, salt `mcp-google-multi:refresh-mac:scrypt:v1`) before HKDF, once per process: every client holds MAC'd tokens, and without a work factor one leaked token would test passphrase guesses at hash speed. For each family the store keeps the subject, the current generation, a SHA-256 of the current token's bytes, the sign-in time and the last-use time.

The length, canonical base64url and MAC checks run before the file lock, with constant-time compares, so a forged token costs one HMAC and never touches the file. A token for an unknown family is refused (the family was revoked, expired, dropped or purged). An older generation for a live family revokes it: it is a rotated-away token, and the MAC proves the server minted it, so nobody without the key can revoke someone else's session by forging one. A newer generation means the store lost a write the client saw (a power loss before the rename reached disk, a backup restore, a lock broken after its lease), and the same generation with another random part means two writers rotated the same generation. Both drop the family too (the client signs in again) but log `ahead` or `mismatch`, not `reuse`, because neither is evidence of theft. The current token rotates: generation plus one, a new random part, the last-use time moved forward, the sign-in time and subject copied forward. A family at the last generation (2^32 - 1) is dropped instead of rotated. The stored hash means the decrypted store holds no usable new-format token. The MAC covers the random part, so an altered current token fails the MAC instead of reaching a drop branch. Revoke and drop lines carry a short tag derived from the family id (`refreshFamilyTagger` computes the same tag from a token, without the store); expiry, `accept` and clock lines carry only a count. No line carries the token or the subject, and lines are written only after the file is.

Files from releases before the format change still load. Every record is validated on load and a malformed one is dropped. Legacy records stay under `active` and `spent` with their old meaning. A legacy token that is still active is exchanged on its next rotation for a new family (generation 0, sign-in time = the legacy record's last-issue time, since the real one was never stored), and the legacy family id is recorded on it. The legacy token joins `spent`, and every legacy `spent` entry of that family keeps revoking the new family. New code adds to `spent` only one entry per migration: each save drops the entries of legacy families with no live record in either format, and the old per-subject cap is gone because it could no longer trigger. Once a process has read a file with no legacy records (a read that fails does not count), it refuses legacy-shaped tokens before the lock as well. An older release reading a new file ignores `format` and `families`, refuses every new token as unknown, and drops the new families the first time it writes. Clients sign in again; nothing is accepted that should not be. A file whose `format` is newer than this release knows is refused rather than read as empty, because an empty read is followed by a write that would erase it.

Lifetimes are optional (`maxAgeSec` from sign-in, `idleSec` from the last issue or rotation; unset means unlimited). Every locked issue and rotation first drops expired sessions of every subject, in both formats, so with a lifetime set the store holds only sessions used within it. Expiry is checked before reuse and before `accept`, so a dead session is refused without asking whether its subject is still served. The last-use time takes the larger of the stored time and the caller's, because `now()` is read before the lock wait and a later writer can hold an earlier time. Timestamps more than five minutes ahead of the clock are pulled back to it on load, so a session written while the clock ran ahead cannot outlive its limit by the size of the jump. A clock that jumps forward makes every session look expired, and the prune deletes them: that fails closed (everyone signs in again), and a prune that drops every session logs that the clock may be wrong. A legacy record has only its last issue or rotation time, which serves as both its sign-in and its last-use time. `purgeTenant` takes no clock, so it neither clamps nor prunes.

A revoke, drop or expiry does not recall access tokens already minted from the family; they live out their `accessTtlSec` (600 s by default).

### A concurrent duplicate is not reuse (`RefreshStore.rotate`, `src/mcp-token.ts`)

Several requests can present a family's current token at once (a fan-out that starts many clients in the same instant, a retried request whose first response was lost). The file lock serializes them: one rotates the family forward, and every other one then presents a token exactly one generation behind the new current one. Strict rotation alone cannot tell that apart from theft, so a losing request used to revoke the family out from under the request that won.

`rotate` takes an optional `fingerprint`, a tag for the presenting client (`clientFingerprint(clientId, userAgent, address, key)`, HMAC-SHA256 under the store's own MAC key, truncated, no I/O) that `/token` computes from the request and the caller never controls directly. Keying it (rather than a bare hash of those inputs) means `by` on disk cannot be brute-forced back to the client_id, user agent or address that produced it by anyone who can only read the store file; computing a fingerprint still needs no more than any `/token` request already carries. Each family keeps the fingerprint of whichever rotation last set its current token (`by`). A presented token one generation behind is read as a concurrent duplicate, not reuse, only when all of: its generation is exactly `f.gen - 1`; now is no earlier than, and at most `REPLAY_WINDOW_MS` (30 s) after, the `usedAt` the rotation that retired it set; the request's fingerprint matches `f.by` (constant-time compare); and re-deriving that token's successor reproduces `f.cur` exactly. That last check is what tells the actual retired token from a different token that merely happens to be one generation behind (a forged one, or a sibling family at the same generation): a rotation's successor is no longer drawn at random but derived as `HMAC-SHA256(macKey, "mcp-google-multi refresh r1 successor\n", presented body)[0..16]`, domain-separated from the token MAC itself, so the same input always rotates to the same output and the server can recompute it from the retired token alone. A genuine duplicate gets back that exact successor, with no change to the family (not even `usedAt`) and nothing written to disk beyond whatever the load's own prune already needed; `accept` still runs first, so a subject declared inactive is refused the same way a normal rotation would refuse it. Anything that fails any one of the four conditions (another fingerprint, outside the window, two generations back, a different token at the same generation) still revokes the whole family and logs `reuse`, exactly as before. The log line for an accepted duplicate (`replayed`) carries only the family tag, never the token, the subject or the fingerprint.

A thief who captured the token off the wire sees a different address (and, in practice, usually a different user agent) than the legitimate client, so a stolen token presented anywhere else still revokes on the first divergence. A thief who shares the legitimate client's exact fingerprint and presents within the window of every rotation is not caught by this rule at all: both sides keep drawing the same successor from the same chain indefinitely, since neither presentation is distinguishable from the other once it holds. What this rule guarantees is narrower than "caught on the next rotation": it is caught on the first divergence from that shared chain (a presentation outside the window, from another fingerprint, or more than one generation behind), exactly the cases strict rotation already caught before this rule existed.

### Family cap eviction excludes the just-issued family (`enforceFamilyCap`, `src/mcp-token.ts`)

`maxFamiliesPerSub` evicts a subject's own least-recently-used refresh-token families (by last issue or rotation time) once a new one would put it over the cap; dropping one behaves exactly like revoking it, and only that subject's own families are ever touched. The family just issued (`keepKey`) is excluded from the ranking entirely: a clock step back, or a concurrent rotation's `usedAt = max(usedAt, nowMs)` racing ahead of it under the lock, could otherwise make the brand-new family look like the least-recently-used one and have it evict itself.

### Orphan-.enc scan before minting a key (`anyTokenFileExists`, `src/master-key.ts`)

The hard guard globs the token dir for any `.enc` file instead of checking only the currently registered aliases: an alias removed from the registry, or a partial `GOOGLE_ACCOUNTS` override in one client, must still stop a fresh `MASTER_KEY` from being minted. `TOKEN_STORE_PATH` may relocate the token dir outside `configDir()`, so that directory is scanned directly; the recursive `configDir()` walk then covers both the tenant-namespaced token root (`tenants/<id>`) and any top-level master-key-encrypted registry beside it (a downstream tenant map or invite store). Minting a fresh `MASTER_KEY` over any existing `.enc` file bricks it irreversibly, so the scan has to see them all.

## Admin SDK

### Why admin tools are per-account opt-in (`ADMIN_SCOPES`, `src/auth.ts`)

The Admin SDK requires a Workspace account with admin privileges; consumer @gmail.com accounts always get a 403. Requesting admin scopes on an account that cannot use them would only add consent-screen noise, so they are granted per account (`GOOGLE_ADMIN_ACCOUNTS`, or `admin: true` on the account or its scope profile in `config.json`) instead of globally. `GOOGLE_OPTIONAL_SCOPES` refuses `admin` as a global bundle.

## Networking

### Why the server raises Node's happy-eyeballs timeout (`applyNetTuning`, `src/net-tuning.ts`)

Node enables Happy Eyeballs (`autoSelectFamily`) by default since v20 and gives each address-family connect attempt 250ms (`autoSelectFamilyAttemptTimeout`). On a high-latency link to a distant Google edge, or when the ISP router advertises a dead IPv6 route, that budget aborts the IPv6 attempt *and* the IPv4 attempt, so every Google call fails with `ETIMEDOUT` while `curl` (which waits normally) works. Node itself raised the default to 500ms ([nodejs/node#60334](https://github.com/nodejs/node/pull/60334)) but only from v25.2; every LTS line this package supports ships 250ms, and the real fix (RFC 8305 parallel attempts, [nodejs/node#48145](https://github.com/nodejs/node/issues/48145)) is still open. The server therefore raises the process-wide default to 2000ms at startup. The trade-off is a slower failover when one address family hangs rather than fails fast — acceptable for a personal MCP server, not worth per-request agent plumbing through gaxios and undici. The tuning is skipped whenever the user passes `--network-family-autoselection-attempt-timeout` or `--no-network-family-autoselection` (via CLI or `NODE_OPTIONS`), and it never lowers a value that is already at or above 2000ms.

### How the section-6 API-enablement probe picks its reads (`API_PROBES`, `src/api-probe.ts`)

Probes are selected by the **granted scopes** on the probed account, not by the registered services: probing an ungranted service can only produce `insufficient_scope`, which says nothing about enablement. Services with no no-argument read (Sheets, Docs, Forms) are probed with a GET on a nonexistent id — Google checks `accessNotConfigured`/`SERVICE_DISABLED` before routing, so a 404 still proves the API is enabled. Admin SDK is deliberately unprobed (role-dependent: a 403 on a non-admin account is ambiguous). A connect-level failure aborts the run so section 6 reports one WARN with the syscall code instead of a column of unknowns. The probe uses `getClient`, so an expired-refreshable token may refresh and re-encrypt on disk — the same cache write every tool call performs; `doctor`'s "no mutation" rule bars config/token *destruction*, not the refresh path.

### Why connect failures get their own `network_error` envelope (`netCodeOf`, `src/tools/_errors.ts`)

The Google API path is gaxios → node-fetch → `node:https`. When the happy-eyeballs `AggregateError` (whose `message` is empty) reaches node-fetch, its `FetchError` keeps only the `code`/`syscall` and discards the error object, producing the famously unhelpful `request to <url> failed, reason: ` with the real signal hiding in `error.code`. Feeding `error.code` through `Number()` (built for HTTP statuses) would drop `ETIMEDOUT` and report `upstream_error, retriable: false` — wrong on both counts. `netCodeOf` walks the cause chain (GaxiosError → FetchError; undici `TypeError` → `AggregateError.errors`) for known connect/DNS syscall codes and returns a `network_error` envelope that names the code, marks transient codes retriable, and points at the happy-eyeballs flag. Per-address sub-errors are only available on undici call sites; node-fetch destroys them upstream.

## Discovery client

### POST verb classification order (`cudFromMethod`, `src/discovery-client.ts`)

`POST_UPDATE_VERB` is tested before `POST_DELETE_VERB` so `cancelWipe`, which calls off a pending wipe, the opposite of one, matches on its `cancelWipe` prefix before its trailing `cancel` could otherwise reach the delete list. The update list's state-transition verbs are all reversible and create nothing, so `create` was both the wrong classification and the most permissive one available; `(batch)?` mirrors the delete list, without which every `batchUpdate*` POST fell through to `create`. The delete list deliberately includes verbs with no literal "delete" in them: `archive` (permanent in GA4), the teardown verbs `stop`/`cancel` (a push channel or long-running operation), `wipe`/`invalidate`/`signOut` (device data, codes, sessions), `reset` (a configuration) and `end` (a live conference), each removes something that existed, so the most restrictive write class is the safe default.

### Path-parameter traversal guard (`expandPath`, `src/discovery-client.ts`)

A blank path segment collapses the path and Google routes the resulting trailing-slash URL to the COLLECTION rather than erroring: `sites.get` with `siteUrl:""` came back as the whole site LIST, reported as success. A `.`/`..` segment resolves at URL-parse time, so `../v1/contactGroups` retargets the call at a different endpoint and returns ITS response as success. Both failure modes are silent-wrong (a successful response for the wrong request), so `expandPath` refuses them locally rather than send a different request than the one asked for. `{+param}` keeps its slashes, so every segment of such a parameter is checked individually.

## Executor

### Request bodies on GET/HEAD (`resolveRequestBody`, `src/executor.ts`)

`executeApiMethod` strips request bodies from GET/HEAD requests before dispatch:

- gaxios stringifies any object passed as `data` without checking the HTTP verb, and undici (Node's `fetch`) rejects GET/HEAD requests that carry a body (`Request with GET/HEAD method cannot have body`). A caller-supplied `{}` body on a read tool would therefore crash the request.
- Stripping is lossless: no Google Discovery GET/HEAD method declares a request schema, so there is never a legitimate GET/HEAD body to preserve.
- Write verbs keep the usual semantics: `null`/`undefined` means no body is sent.

## Argument normalization

`src/arg-normalize.ts` renames snake_case `tools/call` argument keys to their declared camelCase twins (e.g. `thread_id` → `threadId`) before SDK validation, at the transport `onmessage` seam. The seam is deliberate: the SDK advertises an EMPTY input schema in `tools/list` for any non-object schema wrapper (pipe/preprocess), so schema-level normalization would blank every tool's advertised parameters, while the JSON-RPC message shape is versioned MCP spec. The rename is lossless by construction (sent key unknown to the schema, camel twin declared, twin not also sent) and each one logs key names — never values — to stderr. Because clients string-encode values for keys absent from the advertised schema, a renamed key's value is also coerced to the declared scalar kind when it parses cleanly (`"2"` → `2` for a number field, `"true"` → `true` for a boolean); declared keys' values are never touched. `GOOGLE_ARG_NORMALIZE=off` disables it.

The same seam has a second job: **unknown-argument screening** (`src/arg-strict.ts`, `GOOGLE_ARG_UNKNOWN`). zod strips undeclared keys before a handler runs, so without screening a misremembered parameter name produces a *successful* call with wrong behavior: `parentId` passed to `drive_create_folder` (which declares `parentFolderId`) is dropped and the folder is created in My Drive root. Because the seam already holds the tool's declared key set, it can see exactly what the schema is about to discard. It never rewrites a key and never touches a value: rewriting on a guess would send a real value to Google, which is worse than refusing. Renaming runs first, so a snake_case twin of a declared key is a fix rather than an unknown argument. Suggestions are tiered (case/separator-insensitive equality, then token subset, then containment, then edit distance) because plain edit distance cannot reach the motivating case: `parentid` to `parentfolderid` is distance 6. When nothing matches, the hint names how sibling tools in the same service spell the concept. The default is `reject`: `warn` reaches stderr only, so the client still sees a confident success for a call the server did not perform. Never screened: keys starting with `_` (MCP and vendor metadata), keys containing `/` (namespaced extensions), the four client-artifact names (`random_string`, the probe some clients send to a tool they read as argument-less, plus `toolCallId`/`tool_call_id`/`tool_call_description`, which bridges have been seen folding into `arguments` instead of `params._meta` where the spec puts them), tools declaring no arguments, and a key whose declared twin the same call also sent (that call already behaves correctly, so it is left alone). A sibling-spelling hint only ever names a tool that is currently advertised in `tools/list`, since naming a hidden one turns a recoverable error into a dead end. Dotted keys are deliberately *not* exempt, since 41 distinct declared parameter names genuinely contain a dot. The escape hatch needs no exemption either: its open-endedness lives in the *values* of `queryParams`/`body`, never in its fixed top-level keys.

The seam also owns one **outbound** job (`withValidationEnvelope`). The SDK validates tool input itself, throws, and catches its own throw in the same `tools/call` handler, returning `{content:[{type:'text',text:<prose>}],isError:true}`. No handler of ours runs, so no envelope exists and the client would get free text with no slug, no hint and no `retriable`, which is precisely the contract break the hint floor exists to prevent. The wrapper converts that frame, and only that frame: a handler's own answer, whether JSON or the account wizard's prose, passes through untouched, because only the SDK's two prefixes (`Input validation error:`, `Output validation error:`) are rewritten. It is wrapped **innermost**, below the metrics tap, because outbound runs outermost-first: the tap must still see the original prose to classify it as `schema_validation`, while the client sees the envelope. The account is recovered from the pending request, since the registry injects the default only after validation has already failed.

## HTTP transport

### Dispatch is per-request and stateless, so a mid-call server request cannot be delivered (`admitted`, `src/http-transport.ts`; `elicitConfirmation`, `src/registry.ts`)

Every `/mcp` POST builds a brand-new `NodeStreamableHTTPServerTransport` with `sessionIdGenerator: undefined, enableJsonResponse: true`, connects it to the resolved server, dispatches the one request, and tears it down; nothing about the transport survives between requests. `enableJsonResponse` answers with a single `Content-Type: application/json` response once the call settles rather than keeping an SSE stream open, so there is no channel left for the server to push a request of its own (such as an `elicitation/create`) mid-call and later read the client's reply: the SDK's own transport `send()` silently drops a server-initiated request in this mode instead of writing it anywhere. `ToolRegistry.elicitConfirmation` therefore refuses outright whenever `policy.transport === 'http'`, before ever calling `elicitInput`, rather than attempting a call that cannot be delivered and would otherwise just hang until the request's own timeout. stdio keeps one connection open for the whole call and is unaffected. Fixing this for real needs either a stateful/session-bound HTTP mode (an SSE stream held open across the confirmation round trip) or adopting the newer `inputRequired` multi-round-trip primitive in place of the deprecated `elicitInput`; both are out of scope for a write-control change.

### Per-server dispatch lock (`serializeFor`, `src/http-transport.ts`)

A `McpServer` captures its transport per request (`protocol.js`), but the gap between `connect()` and the dispatch capturing it would still race under true concurrency, so all traffic to one server runs under one mutex, keyed on the server identity rather than the subject: two subjects mapped onto the same server (the boot server, or a resolver with several subjects sharing one) would otherwise race through that connect gap. Connect, dispatch and disconnect all run inside the mutex, so the next request can never hit "Already connected"; the serialized section settles three ways, the handler finishes, the client disconnects, or the dispatch deadline fires, so neither a client holding the connection open nor a hung upstream can wedge the lock. The transport closes in a `finally` (resetting `server._transport`) before the lock releases. The free core has one lane (the boot server); with `resolveServer` each resolved server gets its own.

### Lane bound (`maxQueuedPerLane`, `src/http-transport.ts`)

Every `/mcp` request runs its connect and dispatch on its resolved server's lane, one at a time, because a `McpServer` holds one connected transport. The lane is a promise chain with no count, so without a bound a caller admitted faster than its lane drains grows the queue for as long as it keeps sending, each entry holding its buffered body. `maxQueuedPerLane` counts a request against its server from the moment `resolveServer` returns until its lane run settles, which covers reading the body, waiting in the queue and running. The check sits before the body read so a refused request never buffers its body, and the count is per server so one caller's full lane never refuses another's. The slot is released in a `finally` around everything after admission: a body error, a batch refusal, a dispatch deadline and a client that left all release it. A request whose client left while it was being authenticated or resolved has already been destroyed, and Node emits neither `end` nor `error` again once listeners attach, so the body read refuses a destroyed request at once rather than waiting forever and holding its slot. The count bounds queue depth, not queue time: each dispatch keeps its own deadline, so a queued request can wait up to `maxQueuedPerLane - 1` deadlines behind hung calls.

### Client-gone skip (`src/http-transport.ts`)

The dispatch deadline and the disconnect listener are both created when a request's lane run starts, so a request waiting in the queue has neither, and `server.requestTimeout` stops applying once the body is fully received. A queued `gmail_send` whose client gave up would therefore still send when its turn came, and the client's retry could send it again. The host registers a `close` listener on the response as soon as the request passes the front guard; at lane entry a set flag, or a destroyed socket, skips connect and dispatch and logs `499 client_gone path=/mcp`. The socket check is needed because Node emits that `close` only on the response currently writing to the socket: a response pipelined behind another on the same connection stays queued, and when the client drops the connection it never emits `close` at all. It only skips work whose response can no longer be delivered, so it is on regardless of options.

### Graceful close (`HttpTransportHost.close({ graceMs })`, `src/http-transport.ts`)

`close()` with no argument cuts every connection at once, as it always has. With `graceMs` one rule governs the close: every request accepted before `close()` began runs to completion and gets its answer delivered within `graceMs`, and a request that arrives after it began is never handled, not even authenticated. The host stops listening, waits for every socket to close and every `handle()` to settle, and only then resolves; after `graceMs` it cuts what is left. Node's `server.close()` cannot be used as is: since Node 19 it calls `closeIdleConnections()`, which skips a socket only while its response has not ended, so a response that has ended but is still flushing (any body larger than the socket buffers, which a `drive_read` or an export easily is) counts as idle and is destroyed mid-body. The host therefore suppresses that call for the duration of `close()` and closes idle sockets itself from its own bookkeeping: every open socket, per socket the number of accepted requests whose response has not settled (raised in the request listener before `handle()`, lowered when that response finishes or closes) together with the last of them, which sockets have accepted any request, and every unsettled `handle()`. At close start a socket that never accepted a request is destroyed, which covers a connection whose first request headers are still arriving. A socket that has accepted requests but has nothing pending is ended at once, a lingering close like any other (next paragraph), not destroyed: nothing pending only means its last response finished writing, and a large one can still sit in the kernel's buffers while a slow client reads it, so a destroy would reset the connection under that tail as soon as the client sends anything more, a request pipelined behind it say. An idle keep-alive client closes its side on that end at once. On every other socket only the last pending response is marked: it gets `Connection: close` if its headers are not yet sent, and the socket is ended when its count reaches zero, which is when that last response finishes, since responses on a connection finish in order. No response ahead of it ever ends the socket, so a call pipelined behind a streaming route response, or a route behind an `/mcp` call that has not answered yet, is still delivered, and a request already waiting on its lane when the close began runs at its turn. A request pipelined after the close began is ignored by the request listener and its connection ends after the last response it owes, which RFC 9112 section 9.6 allows; nothing of it ran, so the client can retry it safely. The client-gone skip still applies at the lane turn: a pre-close request whose socket died is not dispatched. A socket's entry is deleted when its count reaches zero and when the socket closes, because Node never emits `close` on a response still queued behind another, so the default path holds one entry per socket with a request in flight and one per unsettled `handle()`, and a client that drops a connection with requests still queued on it leaves nothing behind. Waiting on `handle()` as well as on sockets covers a request whose client left while it was being authenticated or resolved: its socket is gone but its work is not.

Ending a socket is a lingering close. Destroying it once its last response is flushed, as Node does after a `Connection: close` response, resets the connection whenever the client is still sending, say a large body pipelined after the close began: the kernel answers unread or later input with a reset and drops whatever of the response is still in its send buffer, so a slow reader loses the tail. The host therefore only calls `socket.end()` and waits for the client's FIN to close the socket, or for `graceMs` to end and the rest to be cut; it also disarms the keep-alive timer Node arms when a response finishes, which would otherwise destroy the socket about 6 s later with the same reset. At close start every socket that has accepted a request gets a `destroySoon` that does the same lingering end, since that is the hook Node calls after a `Connection: close` response. A socket with nothing pending is ended the same way (its last response may still be in the kernel's buffers), so a request racing onto an idle served connection after the close began is held by the rule below and keeps the close waiting until `graceMs`. A request that arrives while closing is never answered, so Node never frees it: its response waits in the connection's outgoing queue behind the ones owed, and Node's own pipelining backpressure, which pauses a socket only while written output is backed up, never engages. A client pipelining tiny requests behind a held response could thus grow the heap without limit until the grace ends. So the first such request stops the socket from reading for good: `socket.pause()`, with `resume` replaced by a no-op on that socket, because Node resumes a socket after every parsed request (`parserOnMessageComplete`) and when its output drains. TCP flow control then stops the client. The requests already in the read being parsed still arrive (at most one read, 64 KiB, of input), and their bodies are left unread. Writing needs no reading, so the responses owed are still delivered whole. The cost is that such a socket can no longer see the client's FIN, so it is closed when `graceMs` ends by `closeAllConnections()`; a client that sends nothing after the close still gets the prompt lingering close. A repeat `close({ graceMs })` returns the close under way, keeping the first grace: running the close start again would arm a second timer, and a shorter one would cut what the first still lets finish. `close()` with no argument during a graceful close cuts every connection at once as it always does; the graceful call still resolves once its handlers settle or its grace ends. `close()` waits on each `handle()` through a promise that never rejects: `fail()` cuts a response whose headers are already sent instead of writing a 500 over it, and if answering a failure throws anyway the response is destroyed, so neither `close()` nor the process sees a rejection, and the close tail runs in a `finally`. `graceMs` is validated before anything closes (a number from 0 to 2^31-1), because `setTimeout` fires at once for a larger delay, `Infinity` included, which would cut every connection at the start of the close.

## Remediation hints

### A process-global provider, like the reauth linker (`src/hint-provider.ts`)

`setHintProvider` follows the same shape as `setHttpReauthLink` (`src/reauth-hint.ts`) for the same reason: one process is either the single owner or one multi-tenant host, never both, so there is nothing to key a provider by. Each call site renders `hints()?.render({ kind, ...facts }) ?? <today's literal>`, with the facts only — never pre-rendered text, `scope_unknown` excepted, which also carries a curated service's own string so a provider can choose to keep it verbatim. That `?? <literal>` at every site, rather than a lookup table a host could overwrite, is what makes the single-owner path byte-identical by construction: there is no default table whose drift from the real call sites a test could miss. The validated `resolveServer`/`resolveSubject` refusal returns (`src/http-transport.ts`, `src/oauth-as.ts`) are a narrower version of the same idea: the host supplies a slug and a message rather than pre-rendered JSON or a redirect fragment, and core validates the shape (slug pattern, message charset and length) before it reaches the wire, so a host bug can fail closed to today's generic answer instead of leaking an unvalidated string to an unauthenticated-until-now caller.

## OAuth authorization server

### Federate-and-hold design (`src/oauth-as.ts`)

The server mints its own audience-bound HS256 token for the MCP client (leg A), gates on an owner Google login whose tokens are discarded (leg B), and separately holds per-alias Google tokens unchanged (leg C). It mounts into `HttpTransportHost` as `routes` plus an `authenticate` for `POST /mcp`. All Google/CIMD I/O is injectable so the whole surface is exercised by an offline harness.

### DCR consent interstitial (`/authorize`, `src/oauth-as.ts`)

A self-registered DCR client can pick an arbitrary `redirect_uri`, so before the owner is sent to Google, whose consent screen names only this server, not the requesting app, an approval interstitial names the client and the destination (confused-deputy defense). CIMD clients skip it: their `redirect_uris` come from an issuer-allowlisted document a rogue client cannot forge, so there is nothing to spoof.

### alias_reauth has no client leg (`/authorize`, `src/oauth-as.ts`)

A user-clicked `flow=alias_reauth` link delivers no code to any client, the refreshed token is written server-side for the alias, so it skips the client_id/redirect_uri/PKCE requirements that gate every other flow. The link must be one this server itself signed (`reauthLink`), and `/callback` still binds the completing Google identity to the alias's configured email before accepting the token.

### Owner sign-in browser binding (`toGoogle`, `/callback`, `src/oauth-as.ts`)

The owner sign-in (`flow=owner_gate`) hands the Google leg a signed state. If that state alone were enough to finish it, then, since DCR is open to any client, anyone could register a client with their own `redirect_uri`, approve its consent interstitial themselves, and forward the resulting Google URL; whoever signed in there would have their subject's authorization code delivered to that `redirect_uri`. The redirect to Google therefore also sets a cookie holding 32 random bytes and signs their sha256 into the state (`StatePayload.bind`). `/callback` spends the state, then, for owner_gate only, reads the cookie the state names and compares its hash with `timingSafeEqual`. A missing or different cookie answers 400 `E_BROWSER_MISMATCH` as a plain page: no redirect to the client, no code, and neither `exchangeCode` nor `resolveSubject` runs, so nothing is looked up and no invite is spent. The log line says only `missing` or `mismatch`, never the cookie or the state. The check runs after the replay spend so a refused callback URL cannot be finished later from the browser that holds the cookie. That needs the spend to be recorded and kept: `ReplayGuard` never forgets a live jti (a full guard refuses, 503, instead of evicting its oldest entry, which a flood of cheap sign-in steps could otherwise push out), and the state's slot is reserved when it is minted, so a flood that fills the guard before the callback arrives is refused at `/authorize` and the callback still finds its slot. The guard is in memory and a restart empties it, so states, approvals and authorization codes are signed with a key each AuthServer generates (one per `buildAuthServer` call), not with `MCP_JWT_KEY`, and are checked against the AuthServer's own clock, the one the guard uses: after a restart every sign-in in flight fails verification and starts again, so neither a callback refused before the restart nor a state that was never reserved in the new process can be finished. On success the cookie is cleared.

Each flow gets its own cookie name (`mgm-og-` plus 16 characters of the hash), so two sign-ins started in one browser, say two clients connecting at once, do not overwrite each other. It is `HttpOnly; SameSite=Lax; Path=/; Max-Age=600` (the state TTL): Lax is still sent on the top-level navigation back from Google. On an `https` base the name carries the `__Host-` prefix and the cookie is `Secure`, so no subdomain or plain-http page can plant one. An `http` base drops both: the prefix requires `Secure`, and browsers do not agree on accepting a `Secure` cookie over plain http even on loopback (WebKit has refused it for `localhost`), so the single owner's `http://127.0.0.1` flow would otherwise break. Plain http offers no transport secrecy anyway, and loopback cookies are shared by every port on the host, which only a local process can use. `alias_add` and `alias_reauth` set and check no cookie: the first is bound by the link its minting caller hands out, the second by the signed re-auth link and the alias's own email. The DCR interstitial is sent with `frame-ancestors 'none'` and `X-Frame-Options: DENY`, so another site cannot frame it and steer the owner's click on Approve.

### Code-exchange failures stay in the log (`/callback`, `src/oauth-as.ts`)

A 400 page is a completed response, so the transport's catch-all 500 never sees a failed exchange and cannot sanitize it. `/callback` therefore answers a fixed `invalid_grant` page itself and logs the thrown message through `logSafe`: a line break becomes a literal `\u000a` and the text is cut at 300 characters, so a multi-line upstream error stays one log line and cannot pass for a second one. A host that wraps `exchangeCode` to map Google errors to slugs can keep doing so; the browser sees the fixed page either way.

### CIMD fetch and cache (`fetchCimdDocument`, `src/ssrf-guard.ts`; `CimdClientCache`, `src/cimd-cache.ts`)

`GET /authorize` is unauthenticated, and a `client_id` on an allowlisted issuer with a path never seen before makes the server fetch a document, so that fetch is bounded on its own and in aggregate. `fetchCimdDocument` follows no redirect, as the CIMD draft requires (section 5): the issuer allowlist is checked on the `client_id` URL only, so a followed hop through an open redirect on an allowlisted host would fetch any document, and that document could claim the original `client_id` and skip the consent interstitial. One deadline (8 s) covers every attempt: each attempt's timer is the smaller of its own cap and the time left, and it is armed before the DNS lookup. `dns.lookup` cannot be cancelled: the attempt stops waiting on it, but `getaddrinfo` keeps its libuv threadpool thread until it returns. `fetch` resolves the host again when it connects, and that lookup can hang too, so an attempt that timed out is never retried, wherever it stalled: one fetch leaves at most one hung lookup behind. The default resolver also starts no lookup of its own while 4 it started have not returned, abandoned ones included; that fetch fails at once as transient (`EAI_AGAIN`), with no retry, instead of queueing behind them. The count is process-wide, as the threadpool is, and covers only these lookups, not the one `fetch` makes when it connects. Only a fast transient failure is retried (a reset, a refused connection, a resolver that could not answer this time, but not a timeout and not a name that does not exist), once, and only when the backoff fits in the time left. A failed attempt aborts its own request first, so a refused status hands its connection back without the body being read. The body cap is the draft's recommended 5 KB (section 8.7).

`CimdClientCache` runs at most 4 fetches at once. That cap alone does not bound the threadpool, since a permit is freed when a fetch gives up, not when its lookup returns. The lookup count above bounds the guard's own lookups, and the no-retry rule leaves at most one connect-time lookup per fetch beside them, which is not counted. With the default pool of 4, lookups that hang can still hold every thread until `getaddrinfo` returns, and async file system calls wait meanwhile, but a flood of distinct paths cannot queue the guard's lookups behind them. A host that needs the file system to stay responsive through a resolver outage can start with a larger `UV_THREADPOOL_SIZE`. A request for a `client_id` already being fetched waits on that fetch and takes no permit. The promise the waiters share never rejects: the request that started the fetch settles it from a `finally`, because neither core nor a host installs an `unhandledRejection` handler and Node exits on one. Over the cap `/authorize` answers 503 `temporarily_unavailable` with `Retry-After: 5`, not `invalid_client`, which clients and people read as a permanent misconfiguration. The cap is full exactly while someone floods random paths, so a document that validated in the last 24 hours is served instead of refusing, and a real client keeps signing in. Only a validated document is stored, as the draft requires (section 5.2: no caching of errors or invalid documents). A refetch whose failure says the document went bad (a 4xx other than 408 and 429, a redirect, an oversized or malformed body, a document that does not validate, a name that does not exist, an SSRF block) drops the stored copy, so such a document is never served stale. A failure that says nothing about the document (a timeout, a reset, a resolver that could not answer, HTTP 408, 429 or 5xx) keeps it, and while it validated less than 24 hours ago the request that fetched and every request waiting on it get that copy instead of the error, so an overloaded issuer does not sign every client out. The error itself is never stored, and the copy keeps its age, so the next request asks the issuer again. There is no negative cache: the attack varies the path, so a key on the full `client_id` never hits, a key on the host would refuse the real issuer, and the draft forbids caching errors anyway. The store holds 256 entries and drops the oldest first. The `CIMD busy` line is rate-limited to one a minute in core because over-cap requests arrive at any rate and core is the one place that sees them all.

## Usage metrics

### No-double-counting guarantee (`tapUsageMetrics`, `src/metrics-tap.ts`)

Inbound, the tap records a `tools/call` request's id against its tool name (name only, the transport's method-only, no-params, no-PII rule). Outbound, a JSON-RPC ERROR frame means no handler ran at all, so it is counted here and ONLY here; a handler result, including an `isError` envelope, comes back as a JSON-RPC result rather than an error frame and is counted by the registry wrapper instead. That split between "error frame" and "result" is the whole guarantee: the two counters can never both fire for the same call. A `-32602` further splits on the SDK's message text: an unknown-tool rejection carries a client-typed name (free text, never recorded), while a schema rejection carries a registered tool's name (safe to attribute), `recordValidation` tells them apart by checking the name against the registered tool set rather than trusting the frame's shape alone.

## Embedding

### Server instructions (`createMcpServer`, `src/compose.ts`)

Every entry point builds its MCP server through `createMcpServer(version, { instructions })`, so a host embedding core can send per-session `instructions` in the initialize result without re-deriving the server identity. The CLI entry passes none, and a blank string counts as none: the initialize result then has no `instructions` field at all, byte-identical to before the seam existed.
